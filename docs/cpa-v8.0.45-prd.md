# CPA v8.0.45 兼容升级 PRD

## 1. 文档状态与范围

- 建立日期：2026-10-28。
- 状态：需求已采纳，2026-10-28 用户授权开始实施；进度以任务清单为准。
- 目标 CPA：`v8.0.45`，提交 `ad8bdd3f20bef44f0684b8a6096a216b2c76040d`。
- 现有基线：插件 `0.1.8`，CPA `v8.0.32`，提交 `911f49cbd49f4fe2516979754a7488a3fd14fe64`，C ABI 1 / RPC schema 6。
- 目标接口：C ABI 1 / RPC schema 7；目标 SDK 模块要求 Go `1.26.10`。
- 配套文件：[实施计划](cpa-v8.0.45-plan.md)、[任务清单](tasks.md)。

本 PRD 描述目标行为，不表示当前代码已经具备这些行为。正式支持状态以
[compatibility.md](compatibility.md) 为准；在开始修改 ABI 代码前，先在该文档增加
“v8.0.45 升级中、未验证”记录，保留原有 v8.0.32 验证记录。只有相应验证通过后才能更新支持状态。
分支名 `compatible/cpa-v8.0.45` 不是兼容性证据。

用户已接受兼容要求及改进方向，并在规划文档建立后授权实施。需求、设计约束、执行顺序和验收标准
用于约束 SDK、源码、夹具、版本常量及运行环境的升级；不得以授权实施代替验证证据。

## 2. 背景与上游核查结论

核查范围为 `v8.0.32..v8.0.45`，包含 13 个后续版本、204 个提交，其中 184 个非合并提交。
20 个非合并提交触及 `sdk/pluginabi`、`sdk/pluginapi` 或 `internal/pluginhost`。
这些是上游变更规模，不能等同于本插件必须修改的项目数。

本插件的主要交集分为五类：schema 7 加载兼容、模型注册与凭据关联行为、新的
`host.auth.models` 数据源、按阶段省略请求体、显式刷新 CPA 模型目录。
另有两项随升级必须处理的本地约束：构建工具链和旧目录快照的兼容读取/更新。

| 版本 | 相关上游变化 | 本插件处理原则 |
| --- | --- | --- |
| v8.0.33 | 模型与凭据绑定、排除模型、相对认证路径身份保留、流式行缓冲变化 | 验证真实注册模型与凭据身份；回归大块流、终止及取消 |
| v8.0.34 | 按 channel 获取静态/插件模型定义；调度器锁与快照处理 | 不新增另一套目录或调度器；验证当前调度和目录契约 |
| v8.0.35 | SIWC 凭据绑定管理 | 不接入未使用的 SIWC 专用管理流程 |
| v8.0.36 | SIWC 路径、凭据替换与并发绑定修复 | 覆盖文件凭据身份，不复制 CPA 的绑定逻辑 |
| v8.0.37 | 新增 `host.auth.models` | 作为运行时凭据 ID 与注册模型关联的权威数据源 |
| v8.0.38 | Codex OAuth 行为修复 | 本插件不实现 OAuth 或 executor；无直接迁移项 |
| v8.0.39 | Usage 服务等级、WebSocket 认证等；Go 要求变为 1.26.10 | 升级构建环境；不新增 Usage 消费或 WebSocket 拦截器 |
| v8.0.40 | FrontendAuth 可读取解码后的请求体 | 本插件未注册 FrontendAuth，无直接迁移项 |
| v8.0.41 | API 防护与 Gemini 目录字段 | 回归目录格式，不新增 provider 适配层 |
| v8.0.42 | executor 的重试元数据、count_tokens、thinking 和请求头处理 | 本插件不注册 executor；保留 CPA 的执行、重试及转换语义 |
| v8.0.43 | 重放请求的 `caller_scope` 保留 | 继续验证现有 metadata 契约，不新增重放或代理执行路径 |
| v8.0.44 | RPC schema 7；按阶段省略请求体；调度与 Usage 的 selection ID | 修复加载阻断，采用拦截后省略请求体；不新增 Usage 记账 |
| v8.0.45 | 管理 API 显式刷新模型目录；Gemini 模型前缀修复等 | 提供用户主动刷新再同步；验证公开模型 ID、别名及前缀 |

升级前注册入口严格检查 `req.SchemaVersion == pluginabi.SchemaVersion`，旧 SDK 常量为 6，
因此旧二进制会拒绝 schema 7 生命周期请求。当前实现已升级 SDK；C ABI 仍是 1，不能把 RPC schema 升级误写成 C ABI 升级。

## 3. 目标与非目标

### 3.1 目标

1. 在隔离的官方 CPA v8.0.45 上完成真实动态加载、管理、目录、请求和生命周期验证。
2. 使用 Host 的真实运行时身份及注册模型，降低对浏览器侧调度 ID 重建和逐凭据管理查询的依赖。
3. 采用安全的请求体传递优化，不破坏响应模型核验的请求关联。
4. 保留已有策略及已接受目录的有效内容、修订号和幂等语义，支持明确的升级与回滚。
5. 区分“同步当前注册目录”与“主动刷新 CPA 目录后同步”，每一步成功和失败可观察。
6. 让后续实施可按任务 ID、证据和验收项追踪，不以编译成功替代兼容验证。

### 3.2 非目标

- 不增加账单系统、Usage 观察点、第二套调度器、请求代理或外部管理员运行时依赖。
- 不引入 CPA internal 包，不复制 provider 的 OAuth、重试、thinking 或转换逻辑。
- 不承诺旧 CPA 版本持续受支持；不因 schema 相同而宣称任意 CPA 版本兼容。
- 不解决上游尚未提供的模型列表认证主体、URL、任意 HTTP 状态修改或通用流中止接口。
- 不修改真实部署、真实凭据或线上策略；不提交、推送、创建 PR、打标签或发布。
- 不顺带重构无关 UI、规则引擎、目录存储格式或现有第三方管理集成。

## 4. 不可破坏的行为

- CPA 请求路径是策略执行的权威入口；管理员离线不能绕过模型、凭据或并发限制。
- 只通过官方 ABI、Host 回调和认证管理 API 工作。目录同步不得在生成请求热路径执行。
- `CredentialRef` 的哈希命名空间保持不变；`auth_index` 不是唯一身份，不可用于去重或替代策略指纹。
- 原始 API Key、管理密钥、请求体及请求体摘要不得进入持久化目录、策略或新增日志。
- 目录更新必须全量校验并原子发布；失败保留上次有效目录，不以空数组假装查询成功。
- 生成权限、凭据子集权重、优先级、并发释放、取消和流式终止语义沿用当前模型及 CPA 生命周期。
- 模型列表仍非安全边界；现有身份推断和 HTTP 状态限制必须如实记录。

## 5. 功能需求

### R-01：版本、SDK 与注册契约

- 目标 SDK 固定 `github.com/router-for-me/CLIProxyAPI/v8 v8.0.45`，构建版本满足 Go 1.26.10。
- 延续仓库“只验证并支持单一最新目标”的策略：此候选版本要求 RPC schema 7，不维护 schema 6 运行时适配器。
  上一轮分析中的 schema 6–7 协商方案只适用于额外承诺旧 Host 支持，本任务不引入该承诺。
- 注册、重配置、管理 capabilities、测试和文档必须一致报告 C ABI 1 / RPC schema 7。
- 不支持的 schema 必须在打开/改变持久化状态之前明确拒绝；失败的重配置不能部分生效。
- `cpa_version` 表示构建固定目标，不是握手检测出的实际 Host 语义版本。
- 候选插件版本在实施阶段按既有版本规则统一确定；若提升版本，必须同步 producer 兼容、JSON schema、UI 和文档，不能只改显示文字。

### R-02：请求体传递优化

- schema 7 注册声明 `request_interceptor_omit_body_after: true`。
- 拦截前阶段继续收到请求体；不得无条件声明 `request_interceptor_omit_body_before: true`。
- 原因：响应模型核验通过原始请求体摘要关联没有 RequestID 的转换前响应钩子，且核验可动态开启。
- 测试应验证注册能力以及开启核验、重配置、相同请求体并发、完成和取消时的行为。
- 不扩大日志或持久化数据来实现请求关联，不把“没有请求体”当作核验成功。

### R-03：真实凭据与注册模型目录

- 在认证管理操作中调用 `host.auth.models`，以返回的实际 ID 和模型列表建立关联。
- Host callback ID 必须沿用当前管理请求上下文；不增加监听端口或浏览器保存的管理凭据。
- 按实际 ID 关联 `host.auth.list` 等官方可用元数据，然后仅输出/保存所需字段。
  浏览器或存储只需要指纹时，不额外暴露原始 ID；名称等显示字段不得进入持久化目录。
- 模型名称以 CPA 已注册公开 ID 为准，包括别名、前缀、排除后的结果；不从 provider 原始配置猜测模型。
- 同一个 `auth_index` 可能对应多个真实 ID，必须全部保留。禁止仅凭 index 将不同凭据合并。
- 显式验证格式、重复 ID、必需的来源/provider/停用状态、模型数组和非法模型 ID；有模型归属的条目缺失元数据时，不完整结果不得发布。
- 先用真实 v8.0.45 夹具验证配置型、文件型、停用和 keyless 凭据的元数据覆盖。
  `host.auth.models` 不提供全部显示/状态字段，`host.auth.list` 也会省略部分运行时条目；不能假设两者集合相等。
- 当元数据不足时，允许保留经夹具证明必要的配置元数据适配，但不再用重建 ID 作为模型归属的权威来源。
  若 index 存在歧义，须有可验证的精确关联依据；不能凭位置、第一条匹配或默认启用状态补齐。
- 交叉审查确认的窄例外：Host 独有、身份/provider/index/模型数组均合法且 `models: []` 的条目可以从持久化目录排除，
  因为空集合不为任何模型建立所有者关系。不得据此猜测来源或停用状态；已知元数据的空模型条目仍保留，
  非空未知条目、任何畸形/重复/已知身份错配和缺失 Host 覆盖仍整次失败。UI 明示排除计数。
- 旧 ID 桥接仅在替代路径覆盖所有既有场景后删除。回调失败不得悄悄退回旧路径并报告成功。
- 保持独立目录修订号、`If-Match`、幂等键及健康状态确认。
- 发布前复查标准化后的凭据身份、来源、启用状态和模型集合；忽略无关的观察时间与瞬时错误状态。
  完整 Host 集合（包括被排除的无模型条目的指纹、index、provider 与空模型事实）也参与双读比较；
  检测到增删或变化则明确中止同步。上游没有全局原子注册表修订号，因此两次读取比较只能检测观察到的变化，不能宣称强一致事务。

### R-04：旧目录快照升级与回滚

- 区分“可读取的已知旧快照”与“当前 API 可写入的快照”，不能仅把 `CPAVersion` 改成 v8.0.45。
- 最小迁移对象为格式 1、目录 contract v1、插件 0.1.8 / CPA v8.0.32 的有效已接受状态。
  未知版本、损坏内容、不合法凭据关联或不确定持久化状态仍按既有规则报错/冻结。
- 已知旧快照通过同等结构和关联校验后，保留上次有效目录、修订号、真实生成/接受时间及既有幂等收据。
  不能在打开文件时伪造新时间、重置修订为 0，或静默清空并重新初始化。
- 健康状态需明确指出快照 producer/CPA 来源及需要重同步；`cpa_version` 目标值不得覆盖历史来源证据。
- 兼容读取不等于自动把旧文件改成新版本。首次成功的新目标同步通过现有原子写路径生成下一修订。
- 旧快照内容在管理端离线期间继续作为上次有效目录使用，并保留现有缺失模型显式报错行为；实际生成仍由当前请求/调度路径约束。
- 当前写接口只接受当前目标 envelope；旧 envelope 的新提交不能利用兼容读取入口绕过校验。
- 历史同键同内容重试及换内容冲突的行为须单独测试，不能因迁移混淆已接受修订。
- 回滚先停止 CPA，再恢复升级前的整个状态目录和匹配的 CPA/插件二进制。
  不承诺旧插件可读取新目录；新候选版本写出的策略也须恢复旧版本接受的备份。

### R-05：显式刷新并同步

- 保留“同步 CPA 目录”：读取当前注册状态，不触发外部模型源刷新；面板初次打开仍走此路径。
- 增加用户主动操作“刷新 CPA 模型并同步”，使用一个固定官方管理路由，例如 `POST /v8/management/models/refresh`。
  `/v8/management/routing/model-definitions/refresh` 是同一上游能力的别名，不需依次调用两个路由。
- 不在页面打开、普通刷新、每个模型查询或生成请求时自动触发全局模型源刷新。
- 校验 HTTP 状态与响应 `ok`，刷新失败中止后续发布；刷新成功后重新读取实际注册模型再同步。
  不把全局模型源刷新等同于每个凭据模型关联已刷新。
- UI 明确展示刷新、同步及最终目录生效状态。CPA 刷新成功但插件同步失败时，说明这两个结果，保留旧目录；不能声称两步原子回滚。
- 操作忙碌期间禁用重复按钮；不因操作失败丢弃未保存的规则或核验配置。

### R-06：契约、测试与说明同步

- 新 Host 回调、能力字段、管理刷新路由均须有单元/管理契约测试和真实 CPA 夹具或捕获证据。
- 继续不注册 Usage、FrontendAuth、executor 或重放能力；新增 selection ID、retry-after 等字段不触发无关功能扩展。
- 更新当前版本说明、JSON schema、管理契约、测试步骤和必要架构说明；保留历史验证记录。
- 只记录实际通过的平台与场景。未配置 `CPA_BINARY` 的 integration skip 不能记为兼容测试通过。

## 7. 已知限制与风险

1. Host 目录不是原子快照：双读校验仍有观察窗口，文档及 UI 不应承诺不存在的注册表事务。
2. 元数据覆盖需以夹具为准；缺失条目不能默认启用，保留适配器必须写明必要性及精确边界。
3. 跨版本目录可能陈旧：允许重同步并暴露来源，不自动把旧目录标为当前 Host 的已验证目录。
4. 外部模型源刷新依赖 CPA 的网络/策略，可能只部分完成；插件不能隐藏该错误或伪造回滚。
5. 规划时本地 Go 为 1.26.4，默认 Go proxy 超时。实施时通过显式进程级代理成功取得 SDK 和 Go 1.26.10，保留 checksum 校验。
   Windows 实际使用 UCRT GCC 16.2.0；旧 GCC 8.1 生成的 DLL 不可加载。完整结果见验收记录。
6. 本任务不使用真实 provider 凭据；Linux/Docker、外部管理员和真实 provider 的验证范围须分别记录。
